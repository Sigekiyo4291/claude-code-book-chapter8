# プロダクト要求定義書 (Product Requirements Document)

## プロダクト概要

### 名称
**TaskCLI** - Gitと一体化した開発者向けタスク管理CLIツール

### プロダクトコンセプト
- **ターミナル完結**: タスクの作成・確認・更新・完了まで、すべての操作をターミナル内で完結させ、GUIツールへの画面切り替えをゼロにする
- **Gitとの一体化**: タスクとGitブランチを1対1で紐付け、ブランチ作成・コミット・マージといった開発フローとタスクの状態を自動で連動させる
- **シンプルで高速**: 開発者が本当に必要とする機能だけを提供し、1分で使い始められ、すべてのコマンドが体感で即座に反応する

### プロダクトビジョン
開発者がコードを書くこととタスクを管理することを、同じターミナル・同じ思考の流れの中で自然に行える世界を目指す。
TaskCLIは「今どのタスクのために、どのブランチで作業しているのか」を常に明確にし、
タスク開始からブランチ作成、コミット、マージ、タスク完了までの一連の流れを自動化・支援する。
JiraやAsanaのような重厚なツールではなく、個人開発者や小規模チームが導入初日から使える軽量なツールとして、
開発者の集中力を守ることを最優先とする。

### 提供する価値
- **コンテキストスイッチの削減**: タスク管理のためのブラウザ⇔ターミナル切り替え(現状1日20回以上)をゼロにする
- **タスクとコードの追跡性**: タスク・ブランチ・コミットの紐付けを自動化し、「どのコードがどのタスクのためのものか」を人手を介さず記録する
- **手作業の削減**: ブランチ作成・ブランチ名の命名・コミットメッセージへのタスク番号記載といった定型作業を自動化する

### 目的
- 開発者がターミナルから離れずにタスクを管理できる手段を提供する
- タスクとGitブランチ・コミットの紐付けを自動化し、作業コンテキストの喪失を防ぐ
- タスク管理にかかる時間を現状の半分に削減する
- 将来的にGitHub連携・チーム機能へ拡張可能な基盤を構築する

## ターゲットユーザー

### プライマリーペルソナ: 佐藤健太(29歳、フリーランスエンジニア)
- **基本属性**: 開発歴6年。フリーランスとして受託案件2〜3件と個人プロダクト1件を並行開発
- **技術スタック**: TypeScript / Node.js、VS Code + 統合ターミナル、zsh、Git / GitHub。CLI操作に慣れており、日常的に`git`・`gh`・`npm`を使う
- **現在の課題**:
  - タスクが頭の中やメモ帳に散在しており、「このプロジェクトで次に何をやるんだっけ?」となることが多い
  - GitHub Issuesは使っているが、ローカルの作業(ブランチ・コミット)と連携できていない
  - ブランチ名の付け方が毎回ばらばらで、後から見て何の作業か分からない
  - コミットメッセージにタスク番号を書き忘れる
- **期待する解決策**:
  - ターミナルで完結し、プロジェクト(リポジトリ)ごとにタスクが管理されること
  - `task start` 1コマンドでブランチ作成・切り替えまで済むこと
  - 学習コストが低く、シンプルで速いこと
- **1日の典型的なワークフロー**:
  1. 朝、プロジェクトのディレクトリに移動して残タスクを確認する
  2. 着手するタスクを決めてブランチを切り、実装を開始する
  3. 1日に数回コミットし、区切りでmainにマージする
  4. 午後は別案件のリポジトリに移動し、同様の作業を繰り返す
  5. 作業中に思いついた改善点やバグを、忘れないうちにタスクとして追加する

### セカンダリーペルソナ: 山田美咲(36歳、スタートアップのテックリード)
- **基本属性**: 開発歴12年。メンバー2〜5人の開発チームをリードし、自身も実装を担当
- **技術スタック**: TypeScript / Go、Neovim + tmux、GitHub(PRベースの開発フロー)
- **現在の課題**:
  - チームメンバーが今何をやっているのか、GUIを開かないと分からない
  - 朝会でのタスク確認に毎日15分以上かかっている
  - JiraやAsanaは小規模チームには重すぎ、導入・運用コストが見合わない
  - ペアプロ中に、さっとタスク一覧を画面共有できない
- **期待する解決策**:
  - CLIでチーム全体のタスク状況を素早く確認できること
  - リポジトリ内でタスクデータを共有でき、追加のサーバーやアカウントが不要なこと
  - GitHub連携により、タスク進捗が自動で更新されること(P1以降)
- **1日の典型的なワークフロー**:
  1. 朝会前にチームのタスク状況を確認する
  2. 自身の実装タスクを進めながら、メンバーのPRをレビューする
  3. 新たに見つかった課題をタスク化し、メンバーに割り振る

> **注記**: MVPはプライマリーペルソナ(個人開発者)を主対象とする。セカンダリーペルソナ向けのチーム機能はP2として段階的に提供する。

- KPIの測定は、ユーザーの明示的な同意に基づくアンケート・ヒアリング・公開統計(npm、GitHub)のみで行う

## 機能要件

### コア機能(MVP)

#### 1. タスクの基本操作(追加・一覧・詳細・削除)

**ユーザーストーリー**:
開発者として、作業中に思いついたことを忘れないために、ターミナルから1コマンドでタスクを追加・確認・削除したい

**受け入れ条件**:
- [ ] `task add "<タイトル>"` でタスクを作成でき、自動採番されたID(1から始まる連番の整数)が表示される
- [ ] タイトルは1〜200文字。空文字や200文字超の場合はエラーメッセージを表示し、タスクは作成されない
- [ ] `task add` に `--description "<説明>"` オプションで詳細説明を付与できる
- [ ] 作成したタスクのステータスは `open`、作成日時・更新日時が記録される
- [ ] `task show <id>` でID・タイトル・説明・ステータス・紐付くブランチ・作成日時・更新日時を表示できる
- [ ] `task delete <id>` で確認プロンプト(`y/N`)を表示し、`y` 入力時のみ削除する。`--force` で確認を省略できる
- [ ] 存在しないIDを指定した場合は「タスク #<id> が見つかりません」というエラーを表示し、終了コード1で終了する
- [ ] 削除したタスクのIDは再利用しない

**優先度**: P0(必須)

#### 2. タスクとGitブランチの自動連携

**ユーザーストーリー**:
開発者として、今どのタスクのためにどのブランチで作業しているかを見失わないために、タスク開始時にブランチが自動で作成・紐付けされてほしい

**受け入れ条件**:
- [ ] `task start <id>` で `feature/task-<id>-<slug>` 形式のブランチを作成し、そのブランチに切り替える
- [ ] `<slug>` はタイトルから生成する(英数字以外はハイフンに置換、小文字化、連続ハイフンは1つに集約、最大50文字)。タイトルが英数字を含まない場合(日本語のみ等)は `feature/task-<id>` とする
- [ ] `--branch <name>` オプションで任意のブランチ名を指定できる
- [ ] 同名のブランチが既に存在する場合は、新規作成せずそのブランチに切り替えて紐付ける
- [ ] 開始したタスクのステータスは `in_progress` になり、ブランチ名がタスクに記録される
- [ ] 作業ツリーに未コミットの変更があり、ブランチの切り替えができない場合は、Gitのエラー内容を含むメッセージを表示し、タスクの状態を変更しない
- [ ] `task hook install` で `prepare-commit-msg` フックを導入でき、タスクに紐付いたブランチ上でのコミット時に、コミットメッセージ末尾へ `Task: #<id>` が自動追記される
- [ ] 既に `Task: #<id>` が含まれるコミットメッセージには重複して追記しない
- [ ] 既存の `prepare-commit-msg` フックがある場合は上書きせず、警告を表示して手動での統合方法を案内する

**優先度**: P0(必須)

#### 3. タスクのステータス管理

**ユーザーストーリー**:
開発者として、タスクの進捗を正確に把握するために、タスクのステータスを明確な状態遷移で管理したい

**受け入れ条件**:
- [ ] ステータスは `open`(新規)・`in_progress`(作業中)・`completed`(完了)・`archived`(アーカイブ)の4種類とする
- [ ] 以下の状態遷移のみを許可し、それ以外の遷移はエラーメッセージを表示して拒否する
  - `open` → `in_progress`(`task start`)
  - `open` / `in_progress` → `completed`(`task done`)
  - `completed` → `in_progress`(`task start` による再開)
  - `open` / `in_progress` / `completed` → `archived`(`task archive`)
- [ ] `task done <id>` でステータスを `completed` に変更し、完了日時を記録する
- [ ] `task archive <id>` でステータスを `archived` に変更する。アーカイブしたタスクは `task list` のデフォルト表示から除外される
- [ ] ステータス変更時は更新日時が更新される

**優先度**: P0(必須)

#### 4. シンプルなタスク一覧表示

**ユーザーストーリー**:
開発者として、次に何をやるべきかをすぐ判断するために、プロジェクトのタスクを一目で把握できる一覧が欲しい

**受け入れ条件**:
- [ ] `task list` でID・ステータス・タイトル・ブランチの4列を表形式で表示する(ブランチ未設定は `-`)
- [ ] デフォルトでは `archived` 以外のタスクをID昇順で表示する
- [ ] `--all` オプションで `archived` を含む全タスクを表示する
- [ ] 現在チェックアウト中のブランチに紐付くタスクの行を強調表示(先頭に `*` を付与)する
- [ ] タスクが0件の場合は「タスクがありません。`task add "<タイトル>"` で追加できます」と表示する
- [ ] 全角文字を含むタイトルでも列がずれない
- [ ] 出力先がTTYでない場合(パイプ・リダイレクト時)は色付けを無効化する

**優先度**: P0(必須)

#### 5. データの永続化とプロジェクト初期化

**ユーザーストーリー**:
開発者として、プロジェクトごとにタスクを管理し、必要ならチームとGitで共有するために、タスクデータをリポジトリ内のファイルに保存したい

**受け入れ条件**:
- [ ] `task init` で現在のGitリポジトリのルートに `.task/` ディレクトリと `.task/tasks.json` を作成する
- [ ] 未初期化の状態で `task add` 等を実行した場合は、自動的に初期化してから処理を行う
- [ ] タスクデータはJSON形式で保存し、人間が読める形式(インデント付き)とする
- [ ] 書き込みは一時ファイルへの書き込み後にリネームするアトミックな方式で行い、書き込み中の中断でデータが破損しない
- [ ] 書き込み前に直前の状態を `.task/tasks.json.bak` としてバックアップする
- [ ] `tasks.json` が破損している(JSONとして読めない)場合は、エラーメッセージとバックアップからの復元方法を表示し、データを上書きしない
- [ ] サブディレクトリから実行した場合もリポジトリルートの `.task/` を参照する

**優先度**: P0(必須)

#### 6. Gitリポジトリ外での動作

**ユーザーストーリー**:
開発者として、Gitを使っていないディレクトリでも混乱しないために、Gitリポジトリ外での挙動が明確であってほしい

**受け入れ条件**:
- [ ] Gitリポジトリ外では、カレントディレクトリの `.task/` を使用してタスクの基本操作(add / list / show / done / archive / delete)を利用できる
- [ ] Gitリポジトリ外で `task start` を実行した場合は、ブランチを作成せずステータスのみ `in_progress` に変更し、「Gitリポジトリではないため、ブランチは作成されませんでした」と警告を表示する
- [ ] Gitリポジトリ外で `task hook install` を実行した場合は、エラーメッセージを表示し終了コード1で終了する
- [ ] Gitがインストールされていない環境でも、タスクの基本操作は動作する

**優先度**: P0(必須)

#### 7. ヘルプとエラーメッセージ

**ユーザーストーリー**:
初めてTaskCLIを使う開発者として、ドキュメントを読まずに使い方を把握するために、分かりやすいヘルプとエラーメッセージが欲しい

**受け入れ条件**:
- [ ] `task --help` で全コマンドの一覧と概要を表示する
- [ ] `task <command> --help` で各コマンドの引数・オプション・使用例を表示する
- [ ] `task --version` でバージョンを表示する
- [ ] エラーメッセージは「何が起きたか」と「どうすれば解決できるか」の両方を含む
- [ ] 成功時は終了コード0、ユーザー入力エラー・実行時エラー時は終了コード1で終了する
- [ ] 存在しないコマンドを入力した場合は、類似コマンドを提案する(例: `task lst` → 「もしかして: list」)

**優先度**: P0(必須)

### CLIインターフェース

```bash
# 初期化
task init                                  # .task/ ディレクトリを作成

# タスクの基本操作
task add "ユーザー認証機能の実装"            # タスクを追加
task add "ログイン画面" --description "メールとパスワードでログイン"
task list                                  # タスク一覧(archived以外)
task list --all                            # 全タスク一覧
task show 1                                # タスク詳細
task delete 1                              # タスク削除(確認あり)
task delete 1 --force                      # タスク削除(確認なし)

# ステータス管理・Git連携
task start 1                               # ブランチ作成・切り替え、in_progressへ
task start 1 --branch fix/login-bug        # ブランチ名を指定して開始
task done 1                                # completedへ
task archive 1                             # archivedへ

# Gitフック
task hook install                          # prepare-commit-msgフックを導入
task hook uninstall                        # フックを削除

# ヘルプ
task --help
task <command> --help
task --version
```

**一覧表示の出力例**:
```
ID  Status       Title                      Branch
1   in_progress  ユーザー認証機能の実装      feature/task-1
2   open         データエクスポート機能      -
3   completed    Initial setup              feature/task-3-initial-setup
```

### 将来的な機能(Post-MVP)

#### 8. タスクの絞り込み・検索

`task list --status in_progress` によるステータス絞り込み、`task search "認証"` によるタイトル・説明の全文検索。

**優先度**: P1(重要)

#### 9. 優先度と期限の管理

`task add "緊急バグ修正" --priority high --due 2025-01-20` による優先度(high / medium / low)・期限の設定と、`task list --sort priority` / `--sort due` による並び替え。期限切れタスクの強調表示。

**優先度**: P1(重要)

#### 10. GitHub Issuesとの連携

`task import --github` によるIssuesからのタスク取り込み、`task sync` によるローカルタスクとIssuesの双方向同期。認証はPersonal Access Token(環境変数 `GITHUB_TOKEN` または `gh` CLIの認証情報)を使用する。

**優先度**: P1(重要)

#### 11. タスク完了時の自動処理

`task done <id>` 実行時に、オプションで「mainへのマージ」「リモートへのプッシュ」「GitHub PRの自動作成」を行う。各処理の前に確認を求め、失敗時は以降の処理を中断してタスクのステータスを変更しない。

**優先度**: P1(重要)

#### 12. チーム機能

`task assign <id> @alice` による担当者割り当て、`task list --assignee me` / `task list --team` によるメンバー別表示。

**優先度**: P2(できれば)

#### 13. 作業時間の記録

`task start` から `task done` までの作業時間を計測・記録し、`task show` で累計作業時間を表示する。

**優先度**: P2(できれば)

#### 14. カレンダー表示

`task calendar --week` / `--month` による期限ベースのカレンダー表示。

**優先度**: P2(できれば)

#### 15. タスクテンプレート

`task template create bug-fix` によるテンプレート定義と、`task add --template bug-fix "..."` によるテンプレートからのタスク作成。

**優先度**: P2(できれば)

## 非機能要件

### パフォーマンス
- **コマンド実行時間**: Git操作を伴わないコマンド(add / list / show / done / archive / delete)は、タスク100件の状態で100ms以内に完了する(Node.js起動時間を含まず、一般的な開発用PC: 4コア以上・SSD・メモリ8GB以上で計測)
- **Git操作を伴うコマンド**: `task start` はタスク100件・コミット数1万件規模のリポジトリで500ms以内に完了する
- **一覧表示**: タスク1,000件の状態で `task list` が1秒以内に完了する
- **コミットフック**: `prepare-commit-msg` フックによるコミット処理の遅延は200ms以内とする

### ユーザビリティ
- **学習容易性**: CLIに慣れた開発者が、ヘルプのみを参照して5分以内に add → start → done の基本フローを完了できる(初期ユーザー5人のユーザビリティテストで測定)
- **導入容易性**: `npm install -g` によるインストールから最初のタスク作成まで1分以内で完了できる
- **ヘルプの網羅性**: すべてのコマンドとオプションが `--help` で確認できる
- **エラーメッセージ**: すべてのエラーメッセージに原因と対処方法が含まれる
- **出力の一貫性**: 色付けは補助的な役割にとどめ、色なし環境(`NO_COLOR` 環境変数設定時を含む)でも情報が欠落しない

### 信頼性
- **データ保全**: アトミックな書き込みとバックアップにより、コマンド実行中の強制終了(Ctrl+C等)でタスクデータが破損・消失しない
- **整合性**: Git操作が失敗した場合はタスクデータを変更せず、操作前の状態を維持する
- **破壊的操作の確認**: 削除などの取り消せない操作には確認プロンプトを表示する
- **テスト**: コアロジック(タスク操作・状態遷移・永続化)のテストカバレッジを80%以上とする

### セキュリティ
- **データの局所性**: MVPではタスクデータをローカルファイルにのみ保存し、外部への通信を一切行わない
- **入力の安全性**: ユーザー入力(タイトル・ブランチ名)をシェルコマンドとして解釈しない。Git操作は引数配列で実行し、コマンドインジェクションを防ぐ
- **ブランチ名の検証**: `--branch` で指定されたブランチ名は `git check-ref-format` 相当の規則で検証し、不正な名前は拒否する
- **認証情報の扱い(P1以降)**: GitHubトークンはタスクデータに保存せず、環境変数または既存の認証ヘルパーから取得する

### 互換性
- **対応OS**: macOS(最新2メジャーバージョン)、Linux(Ubuntu 22.04以降)、Windows 10/11(PowerShell・Git Bash)
- **実行環境**: Node.js 20 LTS以降
- **Git**: Git 2.30以降
- **改行コード・パス**: OS間でのパス区切り文字・改行コードの違いによって動作が変わらない

### スケーラビリティ
- **タスク件数**: 1プロジェクトあたり1,000件まで、パフォーマンス要件を満たす
- **大規模データへの備え**: 1万件を超える規模はMVPの保証対象外とするが、データアクセス層を抽象化し、将来SQLiteへ移行できる設計とする
- **データ形式のバージョン管理**: `tasks.json` にスキーマバージョンを含め、将来のフォーマット変更時に自動マイグレーションできるようにする

## スコープ外

MVPでは明示的に以下をスコープ外とする:
- GitHub以外のホスティングサービス(GitLab、Bitbucket等)との連携
- 専用クラウドサービスによる同期(共有はGit経由のみ)
- GUI・Webインターフェース
- 有料プラン・課金機能
- プラグインシステム・カスタムコマンド定義
- Slack・Discord等の外部チャットツール連携
- サブタスク・タスク間の依存関係管理
- 複数リポジトリを横断したタスクの一括管理
